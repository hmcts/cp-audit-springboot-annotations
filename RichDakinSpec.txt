This document provides an analysis of the structure and patterns found in the existing exemplar JSON files, which represent an existing event log format. The goal is to understand the structure and key components to ensure consistency and usability for further processing. The example files are attached to this page at the bottom. This is by no means comprehensive as these are a sample base.

Azure Storage for SIT
General Observations
The JSON files follow a consistent structure with a shared foundation of fields.

Each file represents an event or action logged by a specific service.

Core components are present across all files, with some variations depending on the originating service.

Core Structure
Having reviewed a subset of the data for 2025, we have correlated the information presented in the files into a table. It is not guaranteed this data is complete, as it is a subset of data and from non live. This relies on all events being triggered during the first month of 2025 in testing, which is somewhat unrealistic.

component	The system component responsible for the event (e.g., QUERY_API).
content	The main payload of the audit event.
content._metadata	Metadata associated with the event.data dictionary
content._metadata.causation	A list of related events that influenced this event.
content._metadata.context	Contextual data related to the user or environment.
content._metadata.context.user	The user associated with this event (UUID).
content._metadata.correlation	Correlation identifiers used for tracing events.
content._metadata.correlation.client	The client ID (UUID) associated with this event.
content._metadata.createdAt	The timestamp when this metadata was created.
content._metadata.id	A unique identifier for this event.
content._metadata.name	The event name (e.g., hearing.latest-hearings-by-court-centres).
content.courtCentreIds	The UUID(s) of the court center(s) involved.
content.dateOfHearing	The date of the hearing.
content.publishCourtListStatuses	A status field related to court list publication.
content.sourceId	Identifier of the source entity.
content.sourceType	The type of source entity.
content.targetType	The type of target entity.
origin	The origin service of this event (e.g., hearing-service).
timestamp	The event timestamp.


Updated Data Model (Enriched & Queryable Format)
(Note - This is not final) Below is a view on the data after it has been Enriched and turned into a queryable format. This is a view of the raw JSON data post some simple structuring and optimisation.

Flatten - Converts the nested JSON fields (_metadata.correlation.client, _metadata.context.user) into top-level columns. Making it easier to query with SQL.

Adding Lookup Values - Fields like user_id, client_id and Court_centre_id are mapped to human readable names using reference tables that business users can interpret (See data dictionary)

Changing Data Types - UUID's, Timestamps, and other raw values are converted into appropriate SQL friendly types. (DATE, TIMESTAMP, STRING) which will improve performance and indexing capabilities.

Storing in Delta Format - The JSON is transferred into Delta using Spark (Fabric Notebooks) as referenced in Solution Overview

Common Fields Across All Files
content:

Contains the main metadata and event-specific details.

_metadata:

Located within the content object.

Key fields include:

correlation.client: A unique identifier for the client or session.

name: Describes the specific event or action.

context.user: Identifies the user associated with the event. (Note - This user ID is not tied to a "Real Name" in this data. That data is kept in the User and Groups database held in PGSQL)

id: A unique identifier for the event.

origin:

Identifies the originating service (e.g., sjp-service, defence-service).

component:

Specifies the service component (e.g., COMMAND_API, Courtscheduler.API).

timestamp:

The ISO 8601 timestamp indicating when the event occurred.

3. Service-Specific Variations
Examples of Service-Specific Fields
sjp-service:

Includes additional fields:

format: File format (e.g., PDF).

language: Language of the document (e.g., ENGLISH, WELSH).

mireportdata-service:

Includes a context.session field, which is not present in other services.

listingcourtscheduler-api:

Focuses on scheduling-related events (e.g., process_rota_files).

6. Recommendations
Schema Standardization:

Formalize the shared schema and document service-specific extensions.

Schema Validation:

Implement validation tools to ensure consistency across services.

Partitioning Strategy:

Organize data storage by origin and timestamp for efficient querying.

Metadata Enrichment:

Add an eventType field to simplify classification and filtering.

This analysis provides a comprehensive overview of the existing JSON file format and its structure. Further steps can include implementing schema validation and optimizing storage and query strategies.
