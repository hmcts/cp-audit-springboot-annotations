Every application or system in the Common Platform must produce audit data that records user activity. The Common Platform provides a centralised solution for collecting, storing, and surfacing this data to support forensic audit investigations.

Note: This page covers the requirements and integration guidance for producers — services that send audit data. For information on how audit data is queried and used for forensic reporting, see the Forensic Auditing page.

Requirements
The following requirements apply to every software system within the Common Platform:

FR.01	Access logs	All attempted user actions must be recorded in the audit log with enough detail to identify: the user who attempted the action, what action they attempted, and what they attempted to perform it on.	Must
FR.02	Authorisation logs	All decisions on whether attempted user actions were authorised should be recorded.	Could
FR.03	Recording failures	If a technical problem prevents an audit event from being recorded, the user's attempted action must be rejected. Audit failures must never be silently swallowed.	Must
FR.04	Standard format	Audit data must be produced in the format defined in the Audit Message Format section below, including all mandatory fields.	Must
FR.05	Auditable action scope	Only actions performed by an identifiable user should be audited. Internal system-to-system events that are not attributable to a user action are out of scope, but events that are triggered by user actions should be audited and attributed to the original user action.	Should
FR.06	Audit configuration transparency	The set of endpoints or actions that a service audits (and any that are explicitly excluded) must be documented and visible. There must be a clear rationale for any exclusions. Ad-hoc disabling of audit without justification is not permitted.	Must
On FR.03: This is a deliberate and important constraint. If audit data cannot be written, it means a user action has occurred with no record of it — which undermines the integrity of the audit trail. Services must treat audit write failures as errors that block the user operation, not as background failures to be logged and ignored.

On FR.05: Approximately 80% of current audit volume consists of system-generated events with no direct user attribution. Reducing this noise would significantly improve the performance and cost of the audit system. New services should apply this filter from the outset.

How It Works


Common Platform microservices send audit events as JSON messages to a dedicated Apache ActiveMQ Artemis message broker via JMS. The audit2dsl service reads those messages from the broker and writes them as individual JSON files to an Azure Blob Storage container. Separately, those files are periodically ingested into Azure Fabric for querying by forensic audit officers. The full implementation details of the audit system are documented Audit System. Integration Guide
Choosing an integration approach
How your service sends audit events depends on what framework it is built on. There are currently three paths:

1. Legacy microservice framework (built-in interceptor)
Services built on the CP microservice framework have audit capture built in via an interceptor. The interceptor automatically publishes an audit event to the Artemis broker for every inbound request. No additional integration work is required, but teams should verify:

That the interceptor is enabled and correctly configured for their service.
That audit is not inadvertently disabled for endpoints where it should be active.
That their messages conform to the message format below, in particular the mandatory fields.
2. Spring Boot — annotation-based shared library (in development)
A new shared library is in development that provides annotation-based audit capture for Spring Boot services. This is the preferred integration path for new Spring Boot services, but the library is not yet complete.

Teams building new Spring Boot services now face a choice (see option 3 below). If you are starting a service that will not go to production before the library is ready, consider contributing to or waiting for this library rather than building your own solution.

3. Spring Boot — build your own (current interim path)
If you are building a new Spring Boot service and cannot wait for the shared library, you will need to implement audit capture yourself. A previous shared library exists (used by the AI Document Knowledge system) but it is not recommended for reuse due to its implementation approach.

Your implementation must:

Intercept the relevant user actions (typically at the controller or service boundary).
Construct an audit message conforming to the format below.
Send the message to the Artemis audit broker queue via JMS.
If the JMS send fails, reject the user's request and return an appropriate error (FR.03). Do not allow the user action to proceed and log the failure silently.

What to audit
Audit every action that a user performs that reads, creates, modifies, or deletes data on the platform. This includes both successful and failed attempts (FR.01).

Do not audit:

Purely internal system events with no user attribution (FR.05).
Health check or readiness probe endpoints.
Technical/infrastructure endpoints that carry no business meaning.
Any endpoint that is explicitly excluded from audit must be documented (FR.06). If you are unsure whether something should be audited, err on the side of auditing it.

Handling audit failures
If your service cannot write an audit event — because the Artemis broker is unavailable, the message cannot be serialised, or any other reason — you must reject the user's request (FR.03). Return an appropriate HTTP error response. Do not proceed with the user's action and swallow the audit failure.

This is not optional. A user action with no audit record is a gap in the audit trail that cannot be recovered after the fact.

Audit Message Format
Schema
The audit message is a JSON object with the following structure. Fields marked mandatory must always be present and non-null.

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "CP Audit Message",
  "type": "object",
  "required": ["component", "origin", "timestamp", "content"],
  "properties": {
    "component": {
      "type": "string",
      "description": "The logical component within the service that generated the event. Typically one of COMMAND_API, QUERY_API, EVENT_LISTENER, or SCHEDULER, but other values are valid.",
      "examples": ["COMMAND_API", "QUERY_API"]
    },
    "origin": {
      "type": "string",
      "description": "The name of the service that generated the event, matching the service's deployment name.",
      "examples": ["progression-service", "hearing-management-service"]
    },
    "timestamp": {
      "type": "string",
      "format": "date-time",
      "description": "ISO 8601 timestamp of when the auditable action occurred (not when the message was sent)."
    },
    "content": {
      "type": "object",
      "required": ["_metadata"],
      "properties": {
        "_metadata": {
          "type": "object",
          "required": ["id", "name", "context"],
          "properties": {
            "id": {
              "type": "string",
              "format": "uuid",
              "description": "A unique identifier for this audit event. Must be a UUID generated per event."
            },
            "name": {
              "type": "string",
              "description": "A dot-namespaced identifier for the event type, following the convention <service-name>.<entity>-<action>. Example: progression.audit-court-document. Some services use different conventions — new services should follow the convention above."
            },
            "createdAt": {
              "type": "string",
              "format": "date-time",
              "description": "Timestamp of when the audit event was created. If omitted, the top-level timestamp will be used."
            },
            "context": {
              "type": "object",
              "required": ["user"],
              "properties": {
                "user": {
                  "type": "string",
                  "format": "uuid",
                  "description": "The UUID of the authenticated user who performed the action. This is the CP platform user ID, not a username."
                }
              }
            }
          }
        },
        "action": {
          "type": "string",
          "description": "A human-readable description of the action performed. Examples: Download, Create, Update, Delete, View."
        },
        "caseId": {
          "type": "string",
          "format": "uuid",
          "description": "The CP case ID, if the action relates to a case."
        },
        "hearingId": {
          "type": "string",
          "format": "uuid",
          "description": "The CP hearing ID, if the action relates to a hearing."
        },
        "materialId": {
          "type": "string",
          "format": "uuid",
          "description": "The CP material ID, if the action relates to a material item."
        },
        "courtDocumentId": {
          "type": "string",
          "format": "uuid",
          "description": "The CP court document ID, if the action relates to a court document."
        },
        "caseStatus": {
          "type": "string",
          "description": "The status of the case at the time of the action, if applicable."
        },
        "dateOfHearing": {
          "type": "string",
          "format": "date",
          "description": "The date of the relevant hearing, if applicable."
        },
        "type": {
          "type": "string",
          "description": "The type or category of the entity being acted upon, where relevant."
        },
        "format": {
          "type": "string",
          "description": "The format of the document or material being acted upon, where relevant."
        },
        "language": {
          "type": "string",
          "description": "The language of the document or material, where relevant."
        }
      }
    }
  }
}
Field reference
Top-level envelope
origin	✅ Yes	string	Service name, matching the deployment identifier.
component	✅ Yes	string	Logical component within the service. Common values: COMMAND_API, QUERY_API, EVENT_LISTENER, SCHEDULER. Other values are valid.
timestamp	✅ Yes	ISO 8601 datetime	When the auditable action occurred. Use the time of the user action, not the time the message was constructed.
content	✅ Yes	object	The audit event payload — see below.
content._metadata
_metadata.id	✅ Yes	UUID string	A unique ID for this audit event. Generate a new UUID per event.
_metadata.name	✅ Yes	string	Event type identifier. Follow the convention <service>.<entity>-<verb>, e.g. progression.audit-court-document. Some existing services do not follow this convention; new services should.
_metadata.context.user	✅ Yes	UUID string	The CP platform UUID of the authenticated user who performed the action.
_metadata.createdAt	No	ISO 8601 datetime	When the audit event was created. Falls back to timestamp if omitted.
content — domain fields
Include whichever of these fields are relevant to the action being audited. The more context you provide, the more useful the audit record is for forensic investigations. Where you have the entity ID, always include it.

action	string	Always — a human-readable label for what the user did (e.g. Download, Create, Update, Delete, Approve).
caseId	UUID string	Whenever the action relates to a case - this MUST be included for any case-related action, even if it needs to be derived (such as from the hearingId, materialId, or courtDocumentId)
hearingId	UUID string	Whenever the action relates to a hearing.
materialId	UUID string	Whenever the action relates to a material item.
courtDocumentId	UUID string	Whenever the action relates to a court document.
caseStatus	string	Where the case status is relevant context for the action.
dateOfHearing	date string	Where a specific hearing date is relevant.
type	string	Where the type/category of the entity provides meaningful context.
format	string	For document/material actions where format matters.
language	string	For document/material actions where language matters.
A note on extensibility: The content object is not strictly bounded — services may include additional fields specific to their domain. However, fields that are not defined above may not be indexed or queryable in the audit reporting system. If you believe a new standard field is needed, raise it with the data engineering team.
